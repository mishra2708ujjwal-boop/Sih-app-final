Part 1 · Read this first — the 2-minute version

1.1 What you have

PRANA is a Flutter app for Android that presents itself as a health-monitoring companion paired with a wrist-worn sensor band. It shows heart rate, blood oxygen (SpO2), body temperature, motion, ambient temperature / humidity / air quality, sleep, a 0–100 personal risk score, plain-English recommendations, and an emergency SOS flow with fall detection.

All of the logic for that is written and working: the maths, the personal-baseline learning, the risk scoring, the recommendation text, the fall-detection state machine, the charts, the whole UI.

1.2 What is real vs. simulated

LayerStatusWhat that means
UI, navigation, chartsREALFinished. 5 destinations, custom bottom bar, hand-painted gauge and charts.
Personal baseline learningREALGenuine rolling mean / standard-deviation statistics, persisted to disk.
Risk engine + recommendationsREALGenuine multi-domain weighted scoring with explainable drivers.
Fall detectionREALGenuine impact-spike-then-stillness algorithm over accelerometer magnitude.
Local storageREALshared_preferences. Nothing leaves the phone.
Sensor inputSIMULATEDA timer generates lifelike fake vitals every 2 seconds. No Bluetooth code exists yet.
ML inferenceHAND-CODEDSix sigmoid equations written by hand in Dart. Not a trained neural network. No TensorFlow in the project.
SOS dispatchSIMULATEDShows a hardcoded Delhi GPS string. Sends no SMS, makes no call, reads no real GPS.

So your job is to replace the two SIMULATED / HAND-CODED boxes with real ones. The good news is that the app was built with exactly that swap in mind — both are hidden behind an interface, so nothing else in the app has to change.

1.3 The only two files that matter for integration

Your two plug points

Hardware: lib/features/devices/sensor_data_source.dart defines an abstract class SensorDataSource with four streams. Write a class that implements it and emits real Bluetooth data, and the whole app instantly runs on hardware.

AI/ML: lib/features/ai/inference_service.dart defines an abstract class MLInferenceService with one real method, runInference(List<double> 16 features) → PredictionResult (6 probabilities). Write a class that implements it using TensorFlow Lite, and the whole app instantly runs on a real model.

Both are injected in one place: the PranaHealthController constructor, called from lib/main.dart.

// lib/main.dart — this is where you swap the engine. Today:
ChangeNotifierProvider(
  create: (_) => PranaHealthController(storage: storageService),
)

// After you finish Parts 7 and 8, it becomes:
ChangeNotifierProvider(
  create: (_) => PranaHealthController(
    storage: storageService,
    customSensorSource: BluetoothSensorDataSource(),  // real band
    customMlService:    TFLiteInferenceService(),     // real model
  ),
)

That constructor already accepts both parameters — see lib/core/services/prana_health_controller.dart lines 111–115. You do not need to modify the controller to inject them.

Part 2 · What the app actually is

2.1 The product idea

A wearable band streams biometrics to the phone over Bluetooth Low Energy. The phone — without any internet connection — learns what "normal" looks like for this specific person, runs a small neural network locally to estimate several health risks, combines that with environmental danger (heat, air quality), and produces one explainable number plus an action to take. If it detects a fall or a critical reading, it starts an SOS countdown.

The pitch is personalisation plus offline operation. A generic app says "60–100 BPM is normal". PRANA says "your normal is 64–78 BPM, and you are at 92 while resting, which for you is a +18% deviation" — and it says this in a village with no mobile data during a heatwave.

The Demo Lab is your debugging console

When you wire up real hardware or a real model, this screen is how you check it is actually working.

2.3 Why "offline-first" and "edge AI"

"Offline-first" means there is no server, no API key, no login, and no network call anywhere in the codebase. Persistence is shared_preferences (a small key–value store on the phone). "Edge AI" means inference happens on the phone's CPU rather than in a cloud service — which is what TensorFlow Lite is for, and what Part 8 sets up.

Part 3 · Getting it running

3.1 Prerequisites

  • Flutter SDK 3.47.2 or newer (you have it — flutter --version confirms).
  • Android SDK with platform-tools on PATH (you have it).
  • An Android phone with USB debugging enabled, or an emulator.
  • Java 17 (the Gradle config targets JVM 17).

3.2 First run

cd /d/sih_test_app_new
flutter pub get          # download packages listed in pubspec.yaml
flutter analyze          # static check — should report only 2 pre-existing style infos
flutter run -d chrome    # fastest way to see the UI, no Android build needed

Chrome is the fastest feedback loop for UI work. It cannot do Bluetooth, so once you start Part 7 you must move to the phone.

3.3 Running on your phone

flutter devices                       # find your phone's id
flutter run -d <device-id>            # hot-reload session, best for development
flutter build apk --debug             # produces build/app/outputs/flutter-apk/app-debug.apk

With flutter run, pressing r hot-reloads your Dart changes in under a second, and R does a full restart. Note that hot reload does not re-run the constructor of PranaHealthController — so after you change which sensor source or ML service is injected in main.dart, you need a full restart (R) or a fresh flutter run.

3.4 The Gradle memory fix (already applied)

Why the Android build was failing

android/gradle.properties was asking the Gradle build daemon for an 8 GB Java heap plus 4 GB metaspace. On a 16 GB machine with only ~3 GB actually free, that Java process cannot start, so it dies instantly and the build fails with the confusing message "A new daemon was started but could not be connected to."

It is now set to a sane size:

# android/gradle.properties (current)
org.gradle.jvmargs=-Xmx2G -XX:MaxMetaspaceSize=512m -XX:ReservedCodeCacheSize=256m -XX:+HeapDumpOnOutOfMemoryError

If a build still fails to start the daemon, close memory-heavy apps (browsers, Android Studio, emulators) and then escalate in this order:

cd /d/sih_test_app_new/android && ./gradlew --stop   # kill stale daemons
cd /d/sih_test_app_new && flutter clean             # wipe build caches
# then, in android/gradle.properties, drop to -Xmx1536m
# last resort, add this line: org.gradle.daemon=false

3.5 Common failures and what they mean

MessageCause & fix
A new daemon was started but could not be connected toGradle heap too large for free RAM. See 3.4.
Unable to load asset: assets/models/...The path in code does not match the assets: block in pubspec.yaml, or you forgot flutter pub get after editing it.
MissingPluginExceptionYou added a native package (like a BLE plugin) but did not do a full restart. Stop the app completely and run flutter run again — hot reload cannot register new native plugins.
RenderFlex overflowed by N pixels in the consoleA layout is too wide/tall for the screen. Yellow-black stripes appear in the UI. Fix by wrapping the offending child in Expanded/Flexible, or switching a Row to a Wrap.
App shows no data / gauge stuck at initial valueYou are in hardware mode with no band connected. Go Me → Demo Lab and turn mock mode back on.
