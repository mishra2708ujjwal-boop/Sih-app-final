5.2 Walking one reading through all six stages

Here is the actual code, from lib/core/services/prana_health_controller.dart. This one method is the pipeline — read it once and you understand the app.

Future<void> _onHealthReadingReceived(HealthReading reading) async {
  _currentHealth = reading;

  // ① buffer for the charts — keep the last 50 points only
  _hrHistory.add(reading.heartRate);
  _spo2History.add(reading.spo2);
  _tempHistory.add(reading.bodyTemperature);
  if (_hrHistory.length > 50) _hrHistory.removeAt(0);
  // … same for the other two …

  // ② teach the baseline service, then ask it how abnormal this is FOR ME
  baselineService.recordReading(reading);
  final hrDev     = baselineService.getHrDeviationPercent(reading.heartRate);
  final spo2Drop  = baselineService.getSpo2DropPoints(reading.spo2);
  final tempElev  = baselineService.getTempElevation(reading.bodyTemperature);

  // ③ build the 16-number vector the model expects
  final features = FeatureProcessor.extractFeatureVector(
    health:       reading,
    environment:  _currentEnvironment,
    baseline:     baselineService.currentBaseline,
    sleep:        _currentSleep,
    hrTrendSlope: _computeHrTrendSlope(),
  );
  _lastFeatureVector = features;   // Demo Lab displays this

  // ④ run the model  ← YOUR TFLITE CALL ENDS UP HERE
  _lastPrediction = await mlService.runInference(features);

  // ⑤ turn probabilities into one explainable score
  _currentRisk = riskEngine.calculateRisk(
    prediction: _lastPrediction,
    health: reading, environment: _currentEnvironment,
    hrDeviationPercent: hrDev, spo2DropPoints: spo2Drop,
    tempElevation: tempElev,
  );

  // ⑥ raise an alert if warranted, then repaint the UI
  if (_currentRisk.level == RiskLevel.high ||
      _currentRisk.level == RiskLevel.critical) {
    _appendAlert(_currentRisk);
  }
  notifyListeners();
}
What notifyListeners() does

The controller is a ChangeNotifier. Screens read it with context.watch<PranaHealthController>(). Calling notifyListeners() tells Flutter "my data changed" and every watching widget rebuilds. That is the entire UI-update mechanism — there is no other. So if your new data isn't showing up on screen, the question is always "did a notifyListeners() happen after I set the value?"

Gap to fix later

DeviceInfo.defaultDevice() hardcodes batteryLevel: 88 and rssi: -58. Until you push real values into deviceStatusStream, the Device screen will always show 88% battery and −58 dBm even with a real band attached. Part 7.6 shows how to emit the real ones.

6.5 UserBaseline — shared/models/user_baseline.dart

The learned personal normal, persisted to disk: normalHrMin, normalHrMax, normalSpo2Min, normalTempMin, normalTempMax, normalHrvMin, sampleCount, lastCalibrated, and isCalibrated (true once sampleCount ≥ 20). Defaults come from AppConstants: HR 60–100, SpO2 min 95, temp 36.1–37.2, HRV min 20.

How it learns, from features/baseline/baseline_service.dart:

  • Only readings whose activityLevel contains "rest" or "low" are recorded — you don't want a sprint polluting your resting normal.
  • Rolling buffers capped at 200 samples.
  • Every 20 samples it recalibrates: mean ± max(8.0, 1.645 × stdDev) for HR (then floored at 48 and ceiled at 110 for safety), and analogous bands for SpO2 and temperature.
  • 1.645 standard deviations is the 90% two-sided confidence band — i.e. "90% of your resting readings fall in here".
Practical consequence for hardware testing

When you first connect a real band, the baseline is still the generic default (HR 60–100) and isCalibrated is false. It takes 20 resting readings to calibrate. If your firmware never sets activityLevel to "Resting" or "Low", the baseline will never calibrate and every deviation number will be measured against the generic default. Send "activityLevel": "Resting" when the wearer is still.

Part 7 · HARDWARE INTEGRATION — connecting real sensors

This is the part you asked for most. By the end of it, a real band will be streaming into the app and the Home screen will show live temperature, SpO2 and heart rate.

7.1 The seam you plug into

Here is the entire interface, lib/features/devices/sensor_data_source.dart. Anything that satisfies this contract can drive the whole app:

abstract class SensorDataSource {
  Stream<HealthReading>      get healthStream;
  Stream<MotionReading>      get motionStream;
  Stream<EnvironmentReading> get environmentStream;
  Stream<DeviceInfo>         get deviceStatusStream;

  Future<void> connect(String deviceId);
  Future<void> disconnect();
  Future<void> startScanning();
  Future<void> stopScanning();
  void dispose();
}

A "Stream" in Dart is a pipe you push values into and someone else listens to. You create one with a StreamController: _controller.add(value) pushes, _controller.stream is the read end. Use .broadcast() so multiple listeners are allowed.

File: android/app/src/main/AndroidManifest.xml. Add the permission block above the <application> tag. Right now this file has none at all.

<manifest xmlns:android="http://schemas.android.com/apk/res/android">

    <!-- ===== Android 12 (API 31) and newer ===== -->
    <uses-permission android:name="android.permission.BLUETOOTH_SCAN"

    <uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />

                     android:maxSdkVersion="30" />

    <!-- Declares the app uses BLE. required=false lets non-BLE phones install it. -->
    <uses-feature android:name="android.hardware.bluetooth_le"

    <application
        android:label="PRANA"          <!-- was "sih_test_app_new" -->
        android:name="${applicationName}"
        android:icon="@mipmap/ic_launcher">
        <!-- … leave the rest of the file untouched … -->

Why neverForLocation: since Android 12, Bluetooth scanning can theoretically be used to infer your location, so Google requires you to either request location permission or explicitly declare that you will not derive location from scan results. Declaring neverForLocation is the honest and much less intrusive choice here.

File: android/app/build.gradle.kts. flutter_blue_plus requires API 23+. Pin it explicitly rather than inheriting:

defaultConfig {
    applicationId = "com.example.sih_test_app_new"
    minSdk = 23                      // ← was: flutter.minSdkVersion
    targetSdk = flutter.targetSdkVersion
    versionCode = flutter.versionCode
    versionName = flutter.versionName
}

Finally, permissions declared in the manifest are not automatically granted — on Android 6+ you must also ask at runtime. Add this helper and call it before your first scan:

// lib/features/devices/ble_permissions.dart  (new file)
import 'package:permission_handler/permission_handler.dart';

class BlePermissions {
  /// Returns true only if we may scan AND connect. Call before startScanning().
  static Future<bool> request() async {
    final result = await [
      Permission.bluetoothScan,
      Permission.bluetoothConnect,
      Permission.locationWhenInUse,   // needed on Android ≤ 11 only
    ].request();

    // locationWhenInUse may be permanently denied on Android 12+ and that is fine,
    // so only the two bluetooth grants are mandatory.
    return result[Permission.bluetoothScan]?.isGranted == true &&
           result[Permission.bluetoothConnect]?.isGranted == true;
  }
}

7.5 Step 3 — the firmware data contract, and three traps

Your band should send one JSON object per packet, UTF-8 encoded, over a single BLE notify characteristic. This is the exact contract, derived from the fromJson methods of the three models — not from the doc comment in sensor_parser.dart, which is wrong:

{
  "heartRate":        82.5,        // BPM        → HealthReading
  "spo2":             97.2,        // %          → HealthReading
  "bodyTemperature":  36.85,       // °C wrist   → HealthReading  ★ not "temperature"
  "activityLevel":    "Moderate",  // Resting|Low|Moderate|High
  "steps":            4120,        // int
  "restingHeartRate": 68.0,        // BPM
  "hrvRmssd":         45.0,        // ms

  "accX":             0.08,        // g          → MotionReading
  "accY":             0.14,
  "accZ":             0.98,
  "isFallSuspected":  false,       // bool, optional firmware hint

  "temperature":      31.2,        // °C ambient → EnvironmentReading ★ different key!
  "humidity":         54.0,        // %RH
  "aqi":              48,          // int 0-500
  "heatExposureHours": 1.5         // see 7.11
}
Trap 1 — two different temperature keys

Body temperature is "bodyTemperature". Ambient temperature is "temperature". They coexist in the same flat packet because three different models each pick out the keys they care about. Sending only "temperature" means the body-temp card silently shows the default 36.8 °C forever while the environment card works — a bug that looks like "the thermistor is broken".

Trap 2 — timestamp will destroy your packet

All three models do DateTime.parse(json['timestamp'] as String). If your firmware sends "timestamp": 1724784000000 (a Unix epoch integer, which is the natural thing to send), that cast throws. And because onTelemetryPacketReceived wraps everything in catch (_) {}, the exception is swallowed and the entire packet is discarded with no log line, no error, nothing. The app just looks frozen.

Either omit timestamp entirely (the models default to DateTime.now(), which is what you want anyway — the phone's clock is more trustworthy than a microcontroller's) or send ISO-8601: "2026-08-28T14:30:05Z". Recommendation: omit it.

Trap 3 — the silent catch, in general

While you are bringing hardware up, make the failure loud. Change the catch in bluetooth_sensor_data_source.dart to actually print:

} catch (e, st) {
  // During bring-up you NEED to see malformed packets, not swallow them.
  debugPrint('[PRANA/BLE] dropped packet: $e');
  debugPrint('$st');
}

This single change will save you hours. A dropped packet is invisible otherwise.

The packet above is ~250 bytes. Keep it under ~180 bytes if you can by dropping fields your hardware doesn't measure — every omitted key just falls back to a sensible default. A minimal useful packet is:

{"heartRate":82.5,"spo2":97.2,"bodyTemperature":36.85,"activityLevel":"Resting"}
